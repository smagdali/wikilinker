# Wikilinker Internationalisation Design

Date: 2026-04-14 (supersedes 2026-03-10)

## Goal

Publish Wikilinker in the top 20 Wikipedia languages across all three browser stores (Chrome, Firefox, Safari). One extension per language with its own bloom filter, skip words, UI strings, and localised store listing.

Three matcher tiers:

- **Regex** (15): Latin, Cyrillic, Devanagari, Arabic, Persian. Current regex upgraded to Unicode character classes (`\p{Lu}`, `\p{L}`). Each language needs its own skip words.
- **CJK** (ja, zh, ko): Use `Intl.Segmenter` for word boundaries. Match segmented words and 2-3 word concatenations against the bloom filter. No uppercase/sentence-start rules.
- **RTL** (ar, fa): Regex works (both use spaces). Popup UI needs `dir="auto"`.

Notes:
- Chinese Wikipedia is blocked in mainland China; Chrome Web Store also requires VPN there. Listing still valuable for Taiwan, Hong Kong, Singapore, and diaspora.

## Automation philosophy

This rollout cannot rely on manual per-language work. The goal is that adding or updating a language is a one-command operation from English source material. Specifically:

- **No manual translation**: strings go through Claude API, using a simplified non-idiomatic English source to produce accurate translations.
- **No hand-written skip word lists**: generated from the English list plus language-specific augmentations (articles, particles) via Claude API.
- **No manually captured screenshots**: rendered from synthetic HTML templates in Playwright, fully deterministic.
- **No per-language Xcode projects**: one Safari project, with `Localizable.strings` files driving display name, description, and splash screen copy.
- **Publishing is scripted**: `scripts/publish-all.sh` uploads all 20 ZIPs/XPIs/archives to all three stores from environment credentials.

Native-speaker review is still valuable for skip words and store listings, but should happen before release rather than block the build.

## Matcher changes

### Unicode regex upgrade (regex languages)

Current `extractCandidates` uses `[A-Z]` for uppercase detection. Change to:
- `\p{Lu}` for uppercase letters (covers Latin, Cyrillic, Greek)
- `\p{L}` for any letter
- Unicode flag `/u` throughout

This handles German (ÄÖÜ), Russian (А-Я), Turkish (İŞ), Czech (ČŠ), Polish (ŁŹ), Vietnamese diacritics, etc.

Skip words loaded from `i18n/{lang}/skip-words.json` at build time — the bundler inlines them so there's no runtime fetch.

### CJK matcher (ja, zh, ko)

New matching strategy using `Intl.Segmenter`:
1. Segment extracted text into words: `new Intl.Segmenter(lang, { granularity: 'word' })`
2. For each word-segment, check the bloom filter
3. Also check 2-word and 3-word concatenations (for multi-word titles)
4. No uppercase detection, no sentence-start filter, no `isPartOfLargerPhrase`
5. First-occurrence-only and deduplication rules still apply

`Intl.Segmenter` support: Chrome 87+, Safari 14.1+, Firefox 125+ (all within our target versions).

### RTL support (ar, fa)

Regex approach works — Arabic and Persian use spaces. Popup text elements get `dir="auto"`. Wikilinks render correctly inside RTL context (browser handles bidi).

### Superscript ⓦ glyph

No localization needed — the Unicode circled-W character displays the same in every script. The `aria-hidden="true"` span keeps it invisible to screen readers. Already shipped in v0.6.5.

## Extension build

`node extension/build.js --lang fr`:

1. Copy `extension/` to temp build directory
2. Swap in `i18n/fr/entities-bloom.bin` as entity data
3. Swap in `i18n/fr/skip-words.json` for the matcher
4. Create `_locales/fr/messages.json` from `i18n/fr/messages.json`
5. Patch `manifest.json`:
   - Set `default_locale: "fr"`
   - Set `name: "__MSG_extensionName__"`, `description: "__MSG_extensionDescription__"`
6. For CJK languages, include the segmenter matcher variant
7. For RTL languages, inject `dir="auto"` into popup.html
8. esbuild bundle
9. Output `build/wikilinker-fr.zip`

No more `--bloom` flag (bloom is the only path since v0.6.2).

### Safari: one project, many localizations

Instead of generating a new Xcode project per language, the existing `safari/Wikilinker/` project uses Apple's standard localization mechanism:

- `Localizable.strings` files per language in `safari/Wikilinker/Shared (App)/Resources/{lang}.lproj/`
- Splash screen copy, app display name, and extension description all driven by `NSLocalizedString(...)` in the Swift code
- One app binary, one App Store listing, 20 locales — Apple's intended path for multi-language apps
- Per-language bundle IDs are NOT needed: Apple recommends a single app with localized metadata
- App Store Connect has per-locale fields for name, subtitle, description, keywords, screenshots

This massively simplifies the Safari path compared to the 2026-03-10 plan, which assumed 20 separate Xcode projects.

### Chrome & Firefox: one listing per language

Unlike Safari, Chrome Web Store and Firefox AMO don't have a single-listing-with-locales model. Each language gets its own listing:
- 20 Chrome Web Store extension IDs (one-time registration)
- 20 Firefox AMO add-on IDs
- `browser_specific_settings.gecko.id` differs per language
- `manifest.json` name+description in each language's `_locales/`

## Store listings

Store listings are the primary localised surface. The about page is **not** translated.

### Localised copy per language (`i18n/{lang}/store-listing.json`)

Each language gets ~500 words of localised store copy:
- `name` — short display name (under 50 chars, Chrome limit)
- `shortDescription` — single sentence (under 132 chars, Chrome limit)
- `longDescription` — 3-4 paragraphs covering: what it does, how to use, privacy, credits
- `keywords` — 5-10 localised search terms
- `screenshotCaptions` — one-line caption per screenshot

All generated via `scripts/translate-strings.mjs` from a simplified English source.

### About page stays English-only

The about page (`https://whitelabel.org/wikilinker/`) remains English. Reasons:

1. The about page is post-install history/marketing, not product info — low leverage per install
2. Maintaining 20 about pages against every content change is painful forever
3. The extension's about link already redirects to whitelabel.org; localising that site is a separate, larger project
4. Indie precedent: 1Password, Raycast, Arc, Obsidian all ship multilingual apps with English-only marketing sites

A short footnote on the about page acknowledges this: "Wikilinker works in 20 languages. This page is English-only; product information is available in your language in the Chrome, Firefox, and Safari stores."

Every piece of product information a user needs before and after install lives in the localised store listing.

## Screenshot generation

Screenshots come from **synthetic article templates**, not live news sites.

### Why synthetic

- Live news URLs 404, paywall, redesign, and change content
- Finding "uncontroversial" articles in each language requires native-speaker judgment per release
- App Store reviewers sometimes flag geopolitically sensitive content
- Synthetic content is deterministic, CI-friendly, and consistent across the store grid

### Template approach

1. Three English source templates in `i18n/article-templates/`:
   - `science.html` — ~400 word article on a universally-safe science topic (e.g. the Eiffel Tower, photosynthesis)
   - `biography.html` — biographical article on a widely-known historical figure (Marie Curie, Leonardo da Vinci)
   - `history.html` — historical event article (Voyager missions, Gutenberg press)
2. Each template has:
   - Realistic news-site chrome (header, byline, date, paragraph body)
   - Enough mentions of known entities that Wikilinker produces 10-20 links
   - Neutral topic — no politics, religion, or current affairs
3. Article bodies translated once per language via Claude API, stored in `i18n/{lang}/article-translations/`
4. Playwright renders the template with the correct language's content, runs the built extension, captures:
   - Desktop 1280×800 (Chrome/Firefox stores)
   - iPhone 1284×2778 (App Store)
   - iPad 2048×2732 (App Store)
5. Promo images (440×280 and 1400×560) rendered from separate HTML templates with localised tagline

Output: `i18n/{lang}/screenshots/*.png`

## Publishing pipeline

### Chrome Web Store

- Existing `scripts/publish.sh` (via `chrome-webstore-upload-cli`) extended to take `--lang fr`
- Each language has its own extension ID, credentials in `.env.publish`
- Localised listing copy uploaded via Chrome Web Store API (it supports localised metadata per listing)

### Firefox AMO

- Existing `scripts/publish.sh` extended for web-ext with `--lang fr`
- Each language has its own AMO add-on ID
- Metadata via API

### Safari App Store

- `scripts/publish-safari.sh`:
  - `xcodebuild archive` (one archive, contains all localizations)
  - `xcrun notarytool submit`
  - Metadata per-locale updated via App Store Connect API (store name/description/keywords per locale)
- One universal build, 20 localised App Store Connect entries

### Orchestration

`scripts/publish-all.sh`:
- Runs `build-all-extensions.sh` (20 ZIPs, 20 XPIs, 1 Safari archive)
- For each language: publish Chrome, Firefox
- For Safari: one archive upload, then metadata sync for all 20 locales
- Logs results per store per language

## Testing

- Existing 78-test suite runs against English by default
- Add `--lang` flag to test runner for language-specific tests
- Per-language validation: matcher with `--debug` against one synthetic article, assert false-positive rate < threshold
- CJK tests: verify `Intl.Segmenter` integration with known Japanese/Chinese/Korean entities
- RTL tests: verify popup renders correctly with Arabic/Persian strings (snapshot or visual)

## Rollout order

1. **Infrastructure first** (Phases 1-3): lang config, data pipeline, matcher upgrades, build parameterisation. Ship as v0.7.0 with English only — proves the pipeline works without expanding store presence.
2. **Pilot language** (French): Full end-to-end through stores. Flush out real-world issues before scaling.
3. **Tier 1** (de, es, it, pt, nl, sv — Western European, low-risk): 6 languages in one release wave.
4. **Tier 2** (ru, uk, pl, cs, tr, id): Cyrillic + more European.
5. **Tier 3** (ja, zh, ko): CJK — new matcher path, needs native-speaker smoke test.
6. **Tier 4** (ar, fa, hi): RTL + Devanagari.

At each tier, watch review queues, crash reports, and user feedback before proceeding.
